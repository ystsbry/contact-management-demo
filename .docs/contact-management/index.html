お問い合わせ管理システム

要件・設計 / 2026-10-11

TL;DR

お問い合わせ管理システムの要件と設計の要約。詳細は各ページを参照。

何を作るか

別サイト（HP）のフォームから届く問い合わせを受け付け、スタッフが管理画面からメールで返信し、対応状況を管理するシステム。お客様とのやり取りはメールで完結し、お客様からの返信メールはシステムが受信して該当の問い合わせに自動で紐付ける。

受付 API

HP のフォームから呼ばれる公開 API。Go / Lambda。

管理画面

スタッフ向け SPA。React / TypeScript。

メール基盤

SES による送信・受信と、受信メールの紐付け処理。

HP そのものは範囲外。HP 側に必要な実装は ページの依頼事項にまとめた。

構成の要点

HP / スタッフ→ CloudFront + WAF→ S3（SPA） / API Gateway→ Lambda（Go）→ DynamoDB / SES / Cognito
  • CloudFront の背後に、SPA（S3）と API（API Gateway → Lambda / Go）を同一ドメインで配置する。
  • データは DynamoDB の単一テーブルに持つ。Lambda から VPC なしで使え、アイドルコストがない。
  • 認証は Cognito。API Gateway の JWT オーソライザーでトークンを検証し、ロールは Cognito グループで表す。
  • メールは SES。受信は SES の受信ルールで S3 に原本を保存し、Lambda が解析して問い合わせに紐付ける。
  • Bot 対策は Cloudflare Turnstile、レート制限は WAF。
  • インフラは Terraform で定義し、GitHub Actions から OIDC でデプロイする（アクセスキーは使わない）。

構成図は ページ。

MVP 機能の要点

  • 受付 API: バリデーション、Turnstile 検証、受付番号の発行、自動返信、二重送信防止。
  • 管理画面: ダッシュボード、一覧・検索、詳細（タイムライン）、ステータス変更、担当者アサイン、メール返信、内部メモ、同一顧客の履歴。
  • メール受信: 返信先アドレスと件名の受付番号で紐付け。自動応答の除外、重複排除。
  • 設定: 問い合わせ種別、ユーザー（Cognito 連携）、メール文面。
  • 通知: 新規、担当割当、お客様返信をメールでスタッフへ。

前提・スコープ・決定事項

この設計が立脚している前提と、これまでに決めたことの記録。

前提

  • お客様は別に存在するホームページ（以下 HP）のフォームから問い合わせる。HP 自体はこのリポジトリの範囲外。
  • このリポジトリでは、HP から呼ばれる 受付 API、社内スタッフが使う 管理画面、メール送受信基盤 を実装する。
  • 受付サイトは 1 つ。マルチテナントは考慮しない。
  • お客様とのやり取りは メールで完結 させる。お客様向けの照会ページやマイページは作らない。
  • お客様からの返信メールは システムが受信し、該当の問い合わせに自動で紐付ける。
  • スタッフへの通知は メールのみ。Slack 等の連携は行わない。
  • 規模は 月数十件、スタッフ数人。自動割当、レポート、SLA 管理は不要。
  • フロントエンドは TypeScript / React、バックエンドは Go、インフラは AWS の Lambda と CloudFront を軸にする。

機能要件（MVP）

MVP として実装する機能の一覧。技術的な実現方法は 03 以降のページ。

1. 受付 API（HP から呼ばれる）

  • 氏名、メールアドレス、電話番号（任意）、問い合わせ種別、本文を受け取り保存する。
  • 入力バリデーションを行い、HP 側が項目ごとにエラー表示できる形式で返す。
  • Bot 対策トークン（Cloudflare Turnstile）を検証する。
  • IP 単位のレート制限を行う（WAF）。
  • CORS で HP のオリジンのみ許可する。
  • 受付番号を発行し、レスポンスで HP に返す。HP はお客様に受付番号を表示する。
  • 同じメールアドレスと本文の送信が 5 分以内に重複した場合は、既存の受付番号を返す（二重登録しない）。
  • 問い合わせ種別の一覧を返す API を提供する（HP のセレクトボックス用）。

2. メール送受信

送信

  • 受付時にお客様へ自動返信メールを送る。件名に受付番号を含め、返信先を受信用アドレスにする。
  • スタッフは管理画面からお客様へ返信メールを送れる。送った内容は履歴に残る。
  • 返信メールは、お客様のメーラーで同じスレッドに並ぶようにヘッダを付与する。

受信

  • お客様からの返信メールを SES で受信し、受付番号をもとに該当の問い合わせへ紐付ける。
  • 紐付け先が見つからないメールは、メール起点の新規問い合わせとして登録する。
  • 自動応答（不在通知など）、ウイルス検知、スパム判定のメールは取り込まない。
  • 同じメールを二重に取り込まない。
  • お客様からの返信を受信したら、ステータスを戻し、担当者へ通知する。
  • 受信メールの添付ファイルは MVP では画面に出さない。原本を S3 に保管し、添付があったことだけ記録して画面に表示する。

3. 管理画面

  • ログイン後のトップに、未対応件数、要返信件数、自分の担当件数、直近の問い合わせを表示する。
  • 一覧: ステータス、種別、担当者、要返信で絞り込み、受付日時の新しい順に表示、ページング。
  • 検索: 氏名、メールアドレス、受付番号、本文のキーワード検索。
  • 詳細: お客様情報、種別、ステータス、担当者、メッセージと内部メモとイベントを時系列に並べたタイムライン。
  • 詳細からの操作: ステータス変更、担当者アサイン、メール返信、内部メモ追加。
  • 同じメールアドレスの過去の問い合わせを一覧表示する。
  • 「要返信」が一覧と詳細で分かる。

4. 認証・権限・設定

  • メールアドレスとパスワードでログインする（Cognito）。
  • 初回ログイン時に仮パスワードから本パスワードへ変更する。
  • パスワードを忘れた場合、メールで届く確認コードで再設定できる。
  • ロールは 管理者 / 担当者 の 2 種類。
ロールできること
管理者すべての操作、ユーザー管理、各種設定
担当者問い合わせの閲覧と対応操作
  • ユーザー管理: 追加（招待メール送信）、ロール変更、無効化、パスワードリセット。
  • 自分のパスワード変更。
  • 問い合わせ種別マスタ: 追加、名称変更、表示順、無効化。
  • メール設定: 送信元の表示名、自動返信の件名と本文、スタッフ通知先アドレス、署名。

5. 通知（スタッフ向けメール）

イベント通知先
新規問い合わせ（フォーム / メール起点）設定した通知先アドレス
担当者アサイン担当者本人
お客様からの返信受信担当者本人。未割当なら通知先アドレス

通知メールには受付番号、氏名、種別、本文冒頭、管理画面の詳細 URL を含める。

6. ステータス

ステータス意味
未対応誰も着手していない
対応中担当者が付いている、または対応を進めている
返信済みスタッフが返信し、お客様の反応待ち
完了対応が終わった

自動遷移: 担当者アサインで 未対応 → 対応中。返信送信で → 返信済み。お客様の返信受信で 返信済み / 完了 → 対応中（担当者あり）または 未対応（担当者なし）。手動変更はどのステータスへも可能。遷移図は ページ。

7. 非機能要件

  • HTTPS のみ。
  • 個人情報（氏名、メール、電話、本文）はログインユーザーのみ閲覧できる。アプリケーションログに本文を出力しない。
  • 性能要件は特になし（月数十件）。
  • 対応ブラウザは最新の Chrome / Edge / Safari。
  • 受信処理は冪等にし、SES や Lambda の再試行で重複登録しない。
  • インフラはコードで管理し、再構築できる。
  • バックアップは DynamoDB のポイントインタイムリカバリを有効にする。

8. HP 側への依頼事項

HP はこのリポジトリの範囲外だが、以下の実装が必要になる。
  • Cloudflare Turnstile のウィジェットを埋め込み、取得したトークンを受付 API に渡す。
  • 受付 API を呼び出し、成功時は受付番号を表示する。
  • バリデーションエラー時は、API が返す項目別メッセージを表示する。
  • 送信ボタンの連打を防ぐ（送信中は無効化）。
  • 問い合わせ種別は種別 API から取得するか、管理画面で登録した ID を固定で埋め込む。

リクエストの流れ

受付（HP から）

1
HP が Turnstile のトークン付きで POST /api/public/inquiries を呼ぶ。
2
CloudFront → WAF（レート制限）→ API Gateway → Lambda api。
3
Lambda api が Turnstile を検証し、バリデーションと重複判定をして DynamoDB に保存する。
4
SES で自動返信をお客様へ、通知をスタッフへ送る。
5
受付番号を返す。

管理画面

1
スタッフが SPA でログインする。SPA は Cognito とやり取りしてトークンを得る。
2
SPA は Authorization: Bearer <アクセストークン> を付けて /api/admin/* を呼ぶ。
3
API Gateway の JWT オーソライザーがトークンを検証する。Lambda api はクレームの cognito:groups でロールを判定する。

メール受信

1
お客様が返信すると、受信ドメインの MX により SES が受け取る。
2
SES の受信ルールが原本を S3 に保存し、Lambda inbound を非同期で起動する。
3
Lambda inbound が原本を解析し、紐付けと保存、通知を行う。詳細は ページ。

IaC と CI/CD

Terraform

  • Terraform（HCL）で定義する。用途別のモジュール（data / auth / api / mail / web）を、環境ごとのルートモジュール（envs/dev、envs/prod）から呼び出す。
  • 状態ファイルは S3 バックエンド（use_lockfile = true、Terraform 1.11 以降）に置く。キーは envs/<env>/terraform.tfstate。
  • infra/bootstrap/ は state バケット、GitHub OIDC プロバイダ、CI 用 IAM ロールを作る。管理者がローカルから一度だけ apply する（state は最初ローカル。apply 後にバケットへ移行できる）。
  • Go の Lambda は Terraform ではビルドしない。make lambda-build が dist/api.zip と dist/inbound.zip を作り（arm64、provided.al2023、mtime 固定で再現可能）、aws_lambda_function の filename と source_code_hash で参照する。
  • SPA は Terraform の管理外。CI で vite build → aws s3 sync → CloudFront のキャッシュ無効化を行う。
  • CloudFront 用の WAF と ACM 証明書は us-east-1 に作る必要があるため、web モジュールにプロバイダエイリアスを渡す。
  • 環境は dev と prod の 2 つ（同じ AWS アカウントを前提）。ルートモジュールのディレクトリと terraform.tfvars で切り替える。

DynamoDB を選んだ理由と代替

選んだ理由

  • Lambda から VPC なしで接続でき、NAT ゲートウェイや RDS Proxy が不要。
  • 月数十件の規模ではほぼ無料枠に収まり、アイドルコストがない。
  • 必要なアクセスパターンが限られており、単一テーブルで無理なく表せる。

割り切った点

  • 本文のキーワード検索はスキャンで行う。数千件までは問題ないが、増えた場合は OpenSearch などを検討する。
  • 集計やレポートが必要になった場合は、DynamoDB Streams から集計テーブルや S3 へ流す。

RDB を希望する場合の代替 ⚠️要確認

  • Aurora Serverless v2（PostgreSQL）+ RDS Data API。Lambda から HTTPS で接続でき VPC 不要。
  • ゼロスケール設定にすると未使用時のコンピュート課金はないが、再開時に十数秒かかる。
  • データモデルは の項目をそのままテーブルに置き換えられる。

受付番号の採番

COUNTER / RECEIPT に対して UpdateItem の ADD value :one を ReturnValues = UPDATED_NEW で実行し、返った値を 6 桁ゼロ埋めする。アトミックなので重複しない。

場面方法
フォームの二重送信SUBMIT#<hash> を attribute_not_exists(PK) 条件で PutItem。失敗したら既存項目の receiptNo を返す

サイズ制限への対応

  • DynamoDB の項目上限は 400 KB。受信メールの bodyText は 100 KB で切り詰め、HTML は保存しない。原本は S3（rawS3Key）にあるので失われない。
  • フォーム本文は 5,000 文字までなので問題ない。

自動返信

  • フォーム受付時に送る。本文は設定値をテンプレートとし、{{name}}、{{receiptNumber}}、{{body}} を置換する。
  • Reply-To は受信用アドレスにする。お客様が自動返信に返信しても紐付く。
  • メール起点の新規問い合わせには自動返信を送らない（自動応答同士のループを避ける）。

受信の仕組み

お客様が返信→ MX: reply.example.com→ SES 受信ルール→ S3 に原本保存→ Lambda inbound を非同期起動→ 解析・紐付け・通知
  • 受信ルールは S3 アクション（原本を raw/<messageId> に保存）と Lambda アクションの順に実行される。
  • Lambda のイベントにはヘッダの要約と、スパム・ウイルス・SPF・DKIM の判定結果が含まれる。本文は S3 から取得する。
  • Lambda の非同期起動は失敗時に 2 回再試行される。最終的に失敗したイベントは SQS のデッドレターキューに送り、CloudWatch アラームで気付けるようにする。

受信 Lambda の処理手順

1
receipt.virusVerdict または receipt.spamVerdict が FAIL なら記録だけして終了。
2
S3 から原本を取得し、MIME を解析する（jhillyerd/enmime）。テキスト本文、HTML 本文、ヘッダ、添付件数を得る。
3
自動応答なら終了。判定は Auto-Submitted が no 以外、X-Auto-Response-Suppress あり、Precedence が bulk / auto_reply / junk、または From が自分の送信元アドレス。
4
紐付け先を決める（下の紐付けルール）。
5
紐付け先が無ければ、メール起点の新規問い合わせを作る。source = EMAIL、種別なし、件名はメールの件名、氏名は From の表示名（無ければローカル部）。受付番号を採番する。
6
メッセージ（INBOUND / EMAIL、rawS3Key 付き）を保存する。SK は MSG#<受信日時>#<sesMessageId> で決定的に作る。
7
問い合わせの lastCustomerMessageAt と needsReply = true を更新し、ステータスが 返信済み / 完了 なら、担当者ありで 対応中、なしで 未対応 に戻す。イベント CUSTOMER_REPLIED（新規なら CREATED）を記録する。
8
受信メールの Message-ID を MSGID# 索引に登録する。
9
SESMSG#<sesMessageId> を条件付きで書く。成功したら通知メール（担当者、未割当なら通知先）を送る。既に存在していたら通知しない。
10
途中で失敗したらエラーを返し、Lambda の再試行に任せる。書き込みキーが決定的なので再実行しても二重にならない。

紐付けルール

次の順で探し、最初に見つかったものを採用する。

1. 宛先アドレスの inquiry+INQ-xxxxxx@→ 2. 件名の INQ-\d{6}→ 3. In-Reply-To / References を MSGID# 索引で照合→ 4. 見つからなければ新規問い合わせ

受付番号が見つかっても該当の問い合わせが存在しない場合は、新規扱いにする。

メール送信に失敗しても保存は成功として 201 を返し、失敗はログとイベントに残す。

SPA なので CloudFront の 403 / 404 を index.html に書き換えて配信する。管理者限定の画面はサイドバーからロールに応じて出し分け、API 側でも拒否する。

各画面の要点

ダッシュボード

  • 件数カードを 3 つ（未対応、要返信、自分の担当）。クリックで該当の絞り込み付き一覧へ。
  • 直近 10 件を一覧と同じ行形式で表示。

一覧

  • 行には受付番号、受付日時、氏名、種別、ステータス、担当者、「要返信」バッジ。
  • 絞り込みは URL のクエリに持ち、ブラウザバックで復元できる。
  • ページングは「次へ」のみ（カーソル方式）。

詳細

  • 上部にお客様情報とステータス・担当者のセレクト。変更は即時保存。
  • タイムラインは古い順。メッセージは送受信で色を分け、内部メモとイベントは控えめに表示。
  • 受信メッセージはテキスト本文のみ表示。添付があれば「添付 n 件（原本を保管、MVP では表示しない）」と出す。
  • 返信フォームは本文のみ。件名は [INQ-000123] Re: {元の件名} で固定。送信前に確認ダイアログ。
  • メモフォームは本文のみ。
  • 同一メールアドレスの過去の問い合わせを下部に一覧。

設定

  • 種別: 名称、表示順、有効/無効の編集。削除はしない（既存の問い合わせが参照するため）。
  • ユーザー: 追加すると Cognito から招待メールが届く。無効化、ロール変更、パスワードリセット。
  • メール: 送信元表示名、自動返信の件名と本文（プレースホルダの説明付き）、通知先アドレス、署名。

ステータス遷移

現在きっかけ次
未対応担当者アサイン対応中
未対応 / 対応中スタッフが返信送信返信済み
返信済み / 完了お客様の返信を受信対応中（担当者あり）/ 未対応（担当者なし）

  • 完了にすると closedAt を記録する。
  • 手動変更とアサインは、同じ問い合わせを別のスタッフが同時に更新した場合に備えて updatedAt を条件にした条件付き更新を行い、競合したら 409 を返す。
