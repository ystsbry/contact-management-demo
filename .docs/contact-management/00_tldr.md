# TL;DR

お問い合わせ管理システムの要件と設計の要約。詳細は各ページを参照。

## 何を作るか

別サイト（HP）のフォームから届く問い合わせを受け付け、スタッフが管理画面からメールで返信し、対応状況を管理するシステム。お客様とのやり取りはメールで完結し、お客様からの返信メールはシステムが受信して該当の問い合わせに自動で紐付ける。

| 成果物 | 内容 |
|---|---|
| 受付 API | HP のフォームから呼ばれる公開 API（Go / Lambda） |
| 管理画面 | スタッフ向け SPA（React / TypeScript） |
| メール基盤 | SES による送信・受信と、受信メールの紐付け処理 |

HP そのものは範囲外。HP 側に必要な実装は「機能要件」ページの依頼事項にまとめた。

## 確定した前提

| 論点 | 決定 |
|---|---|
| 受付サイト数 | 1 つ |
| お客様とのやり取り | メールで完結。照会ページは作らない |
| 返信メールの取り込み | システムが受信して自動で紐付ける |
| スタッフ通知 | メールのみ |
| 規模 | 月数十件、スタッフ数人 |
| 技術スタック | React / TypeScript、Go、AWS Lambda + CloudFront、Terraform |

## 構成の要点

- CloudFront の背後に、SPA（S3）と API（API Gateway → Lambda / Go）を同一ドメインで配置する。
- データは DynamoDB の単一テーブルに持つ。Lambda から VPC なしで使え、アイドルコストがない。
- 認証は Cognito。API Gateway の JWT オーソライザーでトークンを検証し、ロールは Cognito グループで表す。
- メールは SES。受信は SES の受信ルールで S3 に原本を保存し、Lambda が解析して問い合わせに紐付ける。
- Bot 対策は Cloudflare Turnstile、レート制限は WAF。
- インフラは Terraform で定義する。

## MVP 機能の要点

- 受付 API: バリデーション、Turnstile 検証、受付番号の発行、自動返信、二重送信防止。
- 管理画面: ダッシュボード、一覧・検索、詳細（タイムライン）、ステータス変更、担当者アサイン、メール返信、内部メモ、同一顧客の履歴。
- メール受信: 返信先アドレスと件名の受付番号で紐付け。自動応答の除外、重複排除。
- 設定: 問い合わせ種別、ユーザー（Cognito 連携）、メール文面。
- 通知: 新規、担当割当、お客様返信をメールでスタッフへ。

## 未決事項（⚠️要確認）

| 項目 | 内容 |
|---|---|
| DB の選択 | DynamoDB を前提にした。RDB を希望する場合は Aurora Serverless v2 + Data API に差し替える |
| ドメイン | 送信元、受信用、管理画面のドメイン名。Route 53 でホストするか |
| SES 受信リージョン | 東京リージョンは 2023 年 9 月に受信対応と発表されている。エンドポイントは実環境で確認 |
| SES のスレッドヘッダ | SES v2 の Simple 形式で In-Reply-To / References が付くかを実送信で確認 |
| WAF のレート制限 | レートルールの最小閾値と課金を確認 |
